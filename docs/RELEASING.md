# Releasing Teleprompter Plus

Releases are **fully automated** by GitHub Actions (`.github/workflows/release.yml`).
You do **not** build `main.js` locally and drag-drop it into a release anymore.
**Pushing a version tag is the entire release.** CI builds, attests, and publishes.

## Why it works this way (Obsidian's current requirements)

Obsidian's plugin review now runs an automated pipeline on every release and expects:

- **GitHub artifact attestation** on the `main.js` and `styles.css` release assets
  — generated by `actions/attest-build-provenance` in CI.
- **Reproducible build** — CI rebuilds `main.js` byte-for-byte from source, proving
  users run exactly the code in the repo.

Our `release.yml` already satisfies both (it has `id-token: write` + `attestations: write`,
runs `bun run build`, and calls `actions/attest-build-provenance@v2`). A hand-built,
manually-uploaded `main.js` would **fail** these checks — so always release via the tag.

For an **already-listed** plugin, Obsidian's bot auto-detects the new release and refreshes
the community store. **No re-submission, no PR to `obsidianmd/obsidian-releases`.**

## Release checklist

1. **Land all work on `main`** (merge the PR first).
2. **Pick the new version (semver).** New user-facing features → **minor** (`0.10.x → 0.11.0`).
   Bug-fixes only → **patch** (`0.11.0 → 0.11.1`).
   ⚠️ **Never reuse a published version number.** Check the
   [Releases page](https://github.com/JuracyAmerico/obsidian-teleprompter-plus/releases)
   and `versions.json` first.
3. **Bump three files** so they all agree:
   - `manifest.json` → `"version": "X.Y.Z"`
   - `versions.json` → add `"X.Y.Z": "<minAppVersion>"` at the top
   - `CHANGELOG.md` → promote `## [Unreleased]` to `## [X.Y.Z] - YYYY-MM-DD`
4. **Verify the build locally — must be 0 errors** (a broken build = a *failed* release, like 0.10.0):
   ```
   bun run check && bun run build
   ```
5. **Commit + push `main`:**
   ```
   git add manifest.json versions.json CHANGELOG.md
   git commit -m "release: X.Y.Z — <summary>"
   git push origin main
   ```
6. **Tag and push — this triggers the release.** The tag **must equal** `manifest.json`'s
   version and use the **bare `X.Y.Z` format (no `v` prefix)** — the workflow only fires on
   `[0-9]+.[0-9]+.[0-9]+`:
   ```
   git tag X.Y.Z
   git push origin X.Y.Z
   ```
7. **Watch it:** `gh run list --limit 1` (or the repo **Actions** tab). ~30s–2min.
8. **Confirm:** `gh release view X.Y.Z` — expect assets `main.js`, `manifest.json`,
   `styles.css`, `isDraft: false`. The store updates within a short while.

## Common mistakes (the ones we've actually hit)

- **Reusing a published version** (e.g. trying to re-ship `0.10.2`). The store already
  served that number from a different commit — you must bump. *(Hit 2026-06-04.)*
- **`v`-prefixed tag.** `v0.11.0` will **not** trigger `release.yml` (the trigger is the
  bare-number glob). Use `0.11.0`.
- **Tag ≠ manifest version.** Obsidian matches the release tag to `manifest.json`; a mismatch
  is rejected. Bump the manifest *before* tagging.
- **Skipping the local build check.** CI builds the same way; if `bun run build` fails locally
  it fails in CI and you get a *Failed* release. Always run step 4 first.

## What the store will reflect (and known non-blocking warnings)

The community listing renders from the repo README + the published release. After a release the
README changes (credits, feature bullets, screenshots) propagate to the store.

The review pipeline also surfaces **non-blocking** warnings that are inherent to the feature set
and do **not** stop publication:
- *Direct filesystem access* / *shell execution* — the TTS engines (`say`, audio cache) and the
  WebSocket server legitimately need `fs` / `child_process`.
- *CSS lint* — prefer full 6-digit hex and avoid `!important` where practical, but these are
  advisory only.
